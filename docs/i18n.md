# Internationalization (i18n) Architecture

> Status: **proposed / scaffolding** — no i18n code exists yet. This doc is the contract
> every future PR that touches user-visible strings should follow. Discussion welcome
> in PRs; treat this as opinionated defaults, not immovable law.

---

## 1. Why i18n matters

Workforce0's primary user is a **non-technical executive** — VP/Director of Product, CPO,
Chief of Staff. These roles exist in every country; product leadership in Tokyo, São Paulo,
Berlin, and Mumbai all have the same job but do not all work in English. Because
Workforce0 is open-source and self-hosted, shipping English-only silently excludes most of
our addressable audience. Translation is a welcomed community contribution (see
`CONTRIBUTING.md`), and the PRD v3.0 roadmap (v1.2) commits to
*"i18n scaffolding (English + one translation as reference)."* This document defines that
scaffolding.

---

## 2. Principles

1. **Locale detection order** — at request time resolve locale in this order:
   1. Explicit URL param (`?locale=es`) — used for previews and E2E
   2. User setting in DB (`User.locale`)
   3. `locale` cookie (set after first detection or user change)
   4. `Accept-Language` header (browser preference)
   5. Fallback: **English (`en`)**
2. **No hardcoded user-visible strings in React components.** Every label, tooltip, toast,
   empty-state, button, and error message passes through `t('key')`.
3. **Pluralization and date/number formatting** use **ICU MessageFormat** (via `next-intl`).
   Never hand-concatenate plurals (`'${n} item' + (n === 1 ? '' : 's')`).
4. **Strings live as JSON** in `frontend/src/messages/<locale>.json`, one file per locale,
   flat enough to diff cleanly but nested by feature for humans.
5. **English is source of truth.** All other locales are derived. If an English key does
   not exist, no translation for it should exist either.

---

## 3. Stack decision — `next-intl`

We use [**next-intl**](https://next-intl-docs.vercel.app/).

Why:

- First-class Next.js 16 App Router support (server components, middleware, layouts)
- Same `t()` API on server and client — no split mental model
- Native ICU MessageFormat (plurals, selects, rich text)
- Works with `Intl.DateTimeFormat` / `Intl.NumberFormat` directly — no custom wrappers
- Zero runtime lock-in: message files are plain JSON, portable to `react-intl`, `Lingui`,
  or `i18next` if we ever switch

Alternatives considered:

| Library    | Why not                                                       |
| ---------- | ------------------------------------------------------------- |
| `i18next`  | Good, but heavier config surface and less idiomatic with RSC  |
| `Lingui`   | Nice DX, but build-time extraction adds tooling burden for OSS contributors |
| Rolling our own | Burns time we should spend on product                    |

## 4. Proposed file structure

```
frontend/src/
├── messages/
│   ├── en.json       # source of truth, English
│   ├── es.json       # Spanish
│   ├── fr.json       # French
│   ├── de.json       # German
│   └── ja.json       # Japanese
├── i18n/
│   ├── config.ts     # SUPPORTED_LOCALES, DEFAULT_LOCALE
│   └── request.ts    # getRequestConfig — server-side locale resolver
└── middleware.ts     # next-intl middleware for locale routing
```

`i18n/config.ts` (sketch):

```ts
export const SUPPORTED_LOCALES = ['en', 'es', 'fr', 'de', 'ja'] as const;
export type Locale = typeof SUPPORTED_LOCALES[number];
export const DEFAULT_LOCALE: Locale = 'en';
```

## 5. Key format

Keys are **dot-nested by feature**, lowercase-camel leaves:

```
integrations.jira.wizard.step1Title
integrations.jira.wizard.step1Description
dashboard.emptyState.cta
errors.auth.invalidCredentials
```

Rules:

- Keep keys stable — translators depend on them. Renaming a key is a breaking change.
- Group by **feature**, not by screen. A string reused across two screens lives under
  the feature that owns it.
- Never embed English words that might look "neutral" (e.g. `"OK"`) — always translate.

## 6. Contributing a translation

Workforce0 welcomes translation PRs. The loop:

1. Fork the repo.
2. Copy `frontend/src/messages/en.json` to `frontend/src/messages/<locale>.json`
   (use a valid BCP-47 tag — `es`, `pt-BR`, `zh-CN`).
3. Translate **values only**, never keys. Keep ICU placeholders (`{count}`, `{name}`)
   exactly as in English.
4. Add your locale to `SUPPORTED_LOCALES` in `frontend/src/i18n/config.ts`.
5. Test locally:
   ```bash
   # URL param
   open http://localhost:3000/?locale=<locale>
   # or cookie
   document.cookie = 'locale=<locale>'
   ```
6. Open a PR with the `i18n` label. Name it `i18n: add <Language> translation`.

Reviewers check: (a) all keys present, (b) ICU placeholders intact, (c) no untranslated
English leaking through, (d) date/currency formatting sensible for the locale.

## 7. Backend strings

~99% of user-visible text lives in the frontend. The exceptions are **API error
messages** that are surfaced directly to the user (auth failures, validation errors,
integration connection failures).

**v1 rule:** backend error strings are **English-only**. Keep them short, stable, and
machine-parseable (include an `errorCode`). Frontend maps `errorCode` → translated
message.

```ts
// API returns:
{ errorCode: 'JIRA_AUTH_INVALID', message: 'Invalid Jira credentials' }

// Frontend renders:
t(`errors.${errorCode}`) // → "Identifiants Jira invalides"
```

**v1.2+:** wire `next-intl` into the backend for direct translation of server-rendered
emails (digests, notifications) and any error strings not hidden behind an `errorCode`.

## 8. AI Council output is **not** translated

Subtle but important: the AI Council generates briefs, summaries, and action items in
whatever language the source material was in. If the transcript is Spanish, the summary
is Spanish. If Slack messages are a mix of English and Japanese, the summary follows
the dominant language.

**Interface language (the `t()` calls) is controlled by user settings. AI-generated
output language is controlled by input.** Do not over-translate — auto-translating AI
output distorts meaning and frustrates bilingual users.

If a user wants AI output translated, that's a distinct feature (a per-brief "Translate
to…" button) — not i18n's job.

## 9. Date, number, and currency formatting

Always via `Intl` APIs, scoped to user locale. `next-intl` exposes helpers that wrap
these cleanly.

```tsx
import { useFormatter } from 'next-intl';

const format = useFormatter();

format.dateTime(createdAt, { dateStyle: 'medium' });
// en: "Apr 18, 2026"     ja: "2026/04/18"    de: "18.04.2026"

format.number(1234567.89);
// en: "1,234,567.89"     de: "1.234.567,89"   fr: "1 234 567,89"

format.number(49.99, { style: 'currency', currency: 'USD' });
// en: "$49.99"           de: "49,99 $"        ja: "$49.99"
```

Never hand-format (`${n.toFixed(2)}`). Never store a locale-formatted string in the DB.

## 10. Pluralization

Use ICU `plural` — always, even when English looks singular/plural-regular. Other
languages have zero, dual, few, many, other.

```json
{
  "inbox.itemCount": "{count, plural, =0 {No items} one {# item} other {# items}}"
}
```

```tsx
t('inbox.itemCount', { count: items.length });
```

Locales like Russian and Arabic need `few` / `many` buckets — translators add them in
their locale file; English can stay at `one` / `other`.

**Gendered selects** work the same way:

```json
{
  "meeting.host": "{gender, select, female {She hosted} male {He hosted} other {They hosted}} the meeting"
}
```

## 11. RTL (right-to-left) — deferred to v1.3+

Arabic, Hebrew, Persian, and Urdu need RTL layouts. We defer this to **v1.3+** but
**every new component should use CSS logical properties today** so the retrofit is
cheap.

- Use `margin-inline-start` instead of `margin-left`
- Use `padding-inline-end` instead of `padding-right`
- Use `start` / `end` in Tailwind (`ms-4`, `me-4`) instead of `l-4` / `r-4`
- Prefer flex/grid ordering over hardcoded left/right positioning

When we flip the `dir="rtl"` attribute on `<html>` in v1.3, a codebase that's already
logical-property-clean should Just Work.

## 12. Testing translations

Three layers:

1. **Unit/snapshot** — for components with complex pluralization or rich-text
   interpolation, snapshot tests per locale catch regressions when keys change.
2. **Playwright E2E** — run at least one critical-path flow (signup → connect Jira →
   see first brief) in a non-English locale (proposed: Japanese, because its character
   metrics stress-test layout the most).
3. **Lint-time key check** — CI step that diffs keys between `en.json` and each other
   locale file; missing keys become warnings, not errors (translation PRs are a
   welcomed ongoing contribution, not a release blocker).

---

## 13. Maintenance — keeping locales in sync

When an `en.json` key is added but other locales aren't updated in the same PR:

- CI inserts a `"__MISSING__"` sentinel into each non-English locale for that key
- A bot opens an issue tagged `i18n` `help-wanted` listing the missing keys per locale
- At render time, `__MISSING__` falls back to the English value (never shown to users)

The exact automation (GitHub Action, CI script, etc.) is **TBD** — if you want to
build it, open an issue and tag `i18n`.

## 14. Initial locales for v1.0 launch

Proposed starter set, to be revisited after community signal:

| Locale   | Code    | Why                                                                  |
| -------- | ------- | -------------------------------------------------------------------- |
| English  | `en`    | Source of truth                                                      |
| Spanish  | `es`    | Largest non-English OSS contributor audience after Portuguese        |
| Japanese | `ja`    | Enterprise-friendly market; stresses layout (CJK glyph width)        |
| German   | `de`    | Long compound words stress-test UI; strong EU enterprise signal      |
| French   | `fr`    | Broad Francophone reach (EU, Canada, Africa); gendered agreement testbed |

Portuguese (`pt-BR`), Simplified Chinese (`zh-CN`), and Hindi (`hi`) are strong
candidates for the next wave — expected to arrive as community PRs.

## Open questions for reviewers

- How do we handle **email** locale — user setting, or the language the email was
  triggered in?

  staying in-repo? (Likely: when > 10 locales.)

Discuss in the PR that lands the scaffolding. This doc is a starting point, not a
spec — evolve it.
